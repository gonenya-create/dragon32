# מצאי מלא: מה חסר כדי שהמחשב האמיתי יהיה זהה ל-Dragon 32

> **מחקר של Codex, 17.10.2026,** במצב קריאה בלבד, לבקשת גונן ("לא לבנות שום דבר לפני בדיקה ומחקר").
> **אימות:** שיחת Dragon הריצה במחשב שלנו את הממצאים העיקריים, וכולם אומתו:
> - `PMODE 4,4:PCLS` מוחק את התוכנית.
> - `^` חסר.
> - `LIST 20` ו-`RUN 20` מתעלמים מהמספר.
> - `GO TO` עם רווח לא עובד.
> - `&HFF` לא נתמך.
> - `SOUND1,1` נכשל.
> - `PLAY A$` נכשל.
> - `-32768 AND 1` נותן `?FC`.
> - `VAL` חותך מספר ארוך.
>
> **ממצא נוסף של השיחה:** `MEM`, `JOYSTK`, `VARPTR`, `POS` ו-`USR` לא נותנות שגיאה. הן מתפרשות כמשתנים ומחזירות 0 בשקט.

**המסקנה: יש לנו מחשב מדומה אמיתי שמריץ BASIC עצמאי רחב, אבל עדיין אין תאימות מלאה ל־Dragon 32.** הפער העיקרי הוא במבנה התוכנית והזיכרון, בשירותי ה־ROM ובחלקי תחביר. הוספת שמות הפקודות החסרים לבדה לא תסגור אותו. אלה מסקנות מקריאת [המפרש](../rom/src/interp.s), [האתחול](../rom/src/boot.s), [ההרחבה](../rom/src/ext.s) ויתר קובצי המקור.

המחקר נעשה **בקריאה בלבד**. נקראו כל ששת הקבצים ב־`docs/`, קובצי המעטפת שביקשת, מקורות ה־ROM וקוד הבדיקות. לא שונה קובץ, ולא הורצו בנייה או בדיקות שיוצרות קבצים. לכן הסימון **עובד** פירושו שנמצא מימוש ברור בקוד; הוא אינו אישור חדש מבדיקה מול מחשב מקורי.

**המקורות ההיסטוריים**

ההפניות המקוצרות בהמשך מתייחסות למקורות האלה. מספרי העמודים הם העמודים המודפסים:

- **מדריך המתכנת — PRG:** ‏[Dragon 32 Programmer’s Reference Guide](https://colorcomputerarchive.com/coco/Documents/Books/Dragon/Dragon%2032%20Programmers%20Reference%20Guide%20(John%20Vander%20Reyden).pdf), ‏1983. מילון BASIC בעמ׳ 7–35, גרפיקה בעמ׳ 37–69, נספחים בעמ׳ 123–132.
- **Companion:** ‏[The Dragon Companion, Jarvis, 1982](https://archive.worldofdragon.org/browse/downloads/Books/The%20Dragon%2032%20-%20Dragon%20Companion%20-%20Jarvis%20(1982).pdf). מצבי מסך בעמ׳ 5–26; שירותים ואחסון בעמ׳ 33–40; מפת זיכרון בעמ׳ 50 ואילך.
- **Inside:** ‏[Inside the Dragon](https://www.dragondata.co.uk/Publications/InsideTheDragon.pdf). השרת לא אפשר פתיחה מלאה, אך חיפוש ממוקד החזיר קטעים מזוהים, ובהם מפת RAM ושירותי ROM. איני טוען שכל הספר נקרא.
- **מדריך המשתמש:** ‏[An Introduction to BASIC Programming Using the Dragon](https://www.dragondata.co.uk/Publications/BASIC-MAN/DRAGON_32_BASIC_MANUAL_rel-v2.pdf), מאת Richard Wadman. גם כאן חלק מהמידע נגיש באמצעות החיפוש, בעוד פתיחה מלאה נכשלה.
- להשלמה: ‏[המידע הרשמי למשתמשי קוד מכונה](https://dragondata.co.uk/Publications/Info_for_mc_users/Info_For_Machine_Code_Users_original.pdf), ‏[טבלת השגיאות במדריך DragonDOS](https://dragondata.co.uk/Publications/IntroDOS/Intro-DragDOS-v1.pdf), ו־[תוספת Dragon 64](https://dragondata.co.uk/Publications/BASIC-MAN/DD_D64_Supplement.pdf), שמבהירה אילו תכונות נוספו רק בדגם המאוחר.

**חלקים 1–2: המצאי המקורי וההשוואה למכונה שלנו**

ההשוואה מאוחדת עם המצאי, כדי שכל תכונה תופיע לצד מצבה אצלנו. **חלקי** כולל גם מימוש שקיים אך אינו משחזר את כל התחביר או הממשק המקורי. **חסר** מתייחס ל־ROM ולמעטפת הנוכחיים, גם כשההתקן עצמו קיים ב־XRoar.

**מקלדת ועריכת קלט**

במדריך המקורי: `BREAK` מחזיר 3, ‏`CLEAR` מחזיר 12, ‏`SHIFT+CLEAR` מחזיר 92, ‏`SHIFT+0` מחזיר 18. אין ב־VDG המקורי אותיות קטנות אמיתיות: נעשה שימוש בתצוגה הפוכה. מקורות: [מדריך המשתמש, עמ׳ 136](https://www.dragondata.co.uk/Publications/BASIC-MAN/DRAGON_32_BASIC_MANUAL_rel-v2.pdf), [Companion, עמ׳ 5](https://archive.worldofdragon.org/browse/downloads/Books/The%20Dragon%2032%20-%20Dragon%20Companion%20-%20Jarvis%20(1982).pdf).

| פריט | מצב אצלנו והבדל |
|---|---|

**סיכון שצריך לטפל בו מוקדם:** `PMODE 4,4` בוחר שטח שמתחיל ב־⁨`$1800`⁩ ואורכו ⁨`$1800`⁩ בתים. כלומר, פעולת ניקוי יכולה להגיע עד ⁨`$2FFF`⁩, בעוד התוכנית שלנו מתחילה ב־⁨`$1E00`⁩. קיימת חפיפה מחושבת מהקוד. זה **ממצא סטטי שלא שוחזר בהרצה**. המקורות: [חישוב הדף](../rom/src/gfx.s#L179), [תחילת התוכנית](../rom/src/interp.s#L8).

זו רשימת ממשקי התאימות המרכזיים שנמצאו, **לא אישור שכל בית עבודה פנימי מופה ואומת**. המקור אצלנו: [הגדרות המפרש](../rom/src/interp.s#L7), [האתחול](../rom/src/boot.s#L15), [המחרוזות](../rom/src/strings.s#L8), [הגרפיקה](../rom/src/gfx.s#L3).

**ברירות מחדל של גרפיקה**

במקור `PCLEAR` מתחיל בארבעה דפים. תחילת השורה הראשונה הרגילה היא ⁨`$1E01`⁩, אחרי בית אפס ב־⁨`$1E00`⁩. אצלנו הרשומה הראשונה מתחילה ב־⁨`$1E00`⁩ עצמו. המקורות: [מדריך המשתמש, עמ׳ 92](https://www.dragondata.co.uk/Publications/BASIC-MAN/DRAGON_32_BASIC_MANUAL_rel-v2.pdf), [Companion, עמ׳ 35–36](https://archive.worldofdragon.org/browse/downloads/Books/The%20Dragon%2032%20-%20Dragon%20Companion%20-%20Jarvis%20(1982).pdf), [interp.s:8](../rom/src/interp.s#L8).

ההבדל החשוב יותר מהבית היחיד הוא שאצלנו `PCLEAR` אינו מזיז את גבול התוכנית, ו־`CLEAR` אינו שומר אזור לקוד מכונה. לכן `PEEK/POKE` עובדים בחומרה, אבל תוכנית שמשנה את מצביעי BASIC המקוריים לא תקבל את ההתנהגות הצפויה.

**פורמט קלטת**

פורמט הבלוק והשדות מתועדים ב־[תיעוד שימור הקלטות בארכיון](https://archive.worldofdragon.org/index.php?title=Tape%5CDisk_Preservation), בהצלבה עם תיעוד החומרה. מסגרת הבלוק:

```text
55 3C type length payload checksum 55
checksum = (type + length + sum(payload)) & 255
type: 00=header, 01=data, FF=end
```

כותרת הקובץ מכילה 15 בתים:

| היסט | תוכן |
|---|---|
| 0–7 | שם, שמונה תווים |
| 8 | סוג: `00` BASIC, ‏`01` נתונים, ‏`02` בינרי |
| 9 | ASCII: ‏`00` בינרי/מקודד, ‏`FF` טקסט |
| 10 | רציף `00` או מקוטע `FF` |
| 11–12 | כתובת EXEC |
| 13–14 | כתובת טעינה |

אצלנו המסגרת וה־checksum **ממומשים**, אבל `CSAVE` כותב תמיד BASIC ASCII, ו־`CLOAD` מקבל רק את הסוג הזה. הקוד דוחה תוכנית מקודדת או קוד מכונה ב־`FM`. מקור: [tape.s:277](../rom/src/tape.s#L277), [tape.s:492](../rom/src/tape.s#L492).

חשוב להפריד:

- מדף הדפדפן יכול **לייבא קובץ CAS ולשמור את הבלוקים**.
- מכאן לא נובע שה־ROM יודע **לפרש את התוכנית שבתוכו**.
- גם תוכנית טקסט מקורית עלולה להשתמש בפקודות, במצביעים או בקוד מכונה שעדיין חסרים.

הראיות במעטפת: [parseCas](../lab/1982/shelf.js#L147), [הפעלת CLOAD](../lab/1982/shelf.js#L105).

**חלק 4: טקסט בזיכרון או טוקנים**

**המלצתי היא לבחור בטוקנים בתוך RAM כמבנה העבודה הקבוע**, אם היעד נשאר התאמה מלאה למקור. טקסט יישאר דרך נוחה לעריכה, להדבקה ולייבוא/ייצוא. זו המלצה הנדסית הנובעת מהיעד ומממשקי הזיכרון, לא דרישה להעתקת הקוד המקורי.

| נושא | טקסט אצלנו | טוקנים תואמים |
|---|---|---|
| תוכניות מוקלדות רגילות | אפשרי; עדיין צריך להשלים שפה | אפשרי באמצעות קידוד בזמן הכנסת שורה |
| קלטת BASIC מקודדת | נדרש פענוח לטקסט בזמן טעינה | אפשר לשמר את הגוף המקודד |
| קלטת ASCII | כבר נתמכת | נדרש tokenizer; עדיין ניתנת לתמיכה |
| `PEEK/POKE` לתוך התוכנית | רואה ומשנה טקסט שונה מהמקור | מאפשר התאמת בתי התוכנית |
| שינוי מצביעי תוכנית | אינו תואם כיום | אפשרי רק אם מתאימים גם את מפת RAM |
| `LIST` | מציג טקסט שמור | מפענח טוקנים לשמות |
| עריכה חיצונית | פשוטה | דורשת קידוד ופענוח |
| זיכרון | מילים נשמרות באורכן | מילת מפתח לרוב מתקצרת |
| מהירות פענוח | השוואת מחרוזות חוזרת | מאפשר זיהוי ישיר של פקודה |
| חשבון וציור | תלויים בשגרות הקיימות | אינם מואצים אוטומטית |
| קוד מכונה שקורא לשירותי ROM | עדיין חסר | עדיין חסר עד מימוש השירותים |

הבסיס ההיסטורי הוא פורמט הרשומות וטבלאות הטוקנים ב־[Companion, עמ׳ 35–40](https://archive.worldofdragon.org/browse/downloads/Books/The%20Dragon%2032%20-%20Dragon%20Companion%20-%20Jarvis%20(1982).pdf). ההשלכות על הקוד שלנו נובעות מ־[storeline והריצה](../rom/src/interp.s), [הביטויים](../rom/src/basic.s) ו־[EDIT/RENUM](../rom/src/ext.s).

שלוש הבהרות חשובות:

- **טקסט אינו חוסם עקרונית טעינת קלטות מקוריות.** אפשר להמיר טוקנים לטקסט. אבל זו תאימות קבצים בלבד; תמונת הזיכרון עדיין שונה.
- **טוקנים אינם פותרים הכול.** הם לא מתקנים את המספרים, `CLEAR/PCLEAR`, טבלת `USR`, שירותי ⁨`$A000`⁩ או קריאות לכתובות פנימיות.
- **עותק טוקנים שאינו מבוצע לא מספיק.** אם `POKE` משנה את התוכנית, המפרש צריך לבצע את הבתים שהשתנו, ולא עותק טקסט נפרד.

אין כרגע בסיס לאחוז חיסכון בזיכרון או לשיעור האצה. צריך למדוד אותם על אותן תוכניות בשתי הגרסאות.

**מה צריך לשנות במעבר**

המעבר נוגע להכנסת שורות, `LIST`, מנתח הביטויים והפקודות, סריקת `DATA`, חיפוש `ELSE`, הגדרות `FN`, עריכה, מספור, קלטות ומצביעי ההמשך של לולאות ותת־שגרות. המבנה המקושר שכבר קיים חוסך חלק מהעבודה, אבל אינו הופך את המעבר להחלפת פונקציה אחת. ראיות: [interp.s](../rom/src/interp.s), [stmt2.s](../rom/src/stmt2.s), [fn2.s](../rom/src/fn2.s), [ext.s](../rom/src/ext.s).

**אומדן בלבד**, בביטחון נמוך, למפתח מנוסה ב־6809 במשרה מלאה:

| היקף | אומדן |
|---|---|
| מתאם קלטות טוקנים↔טקסט, בלי תאימות RAM | 1–3 שבועות |
| מעבר למבנה טוקנים פעיל, כולל עריכה, קלטות ובדיקות | 4–10 שבועות |
| התאמת מצביעים, ניהול זיכרון ו־`CLEAR/PCLEAR` | תוספת 3–8 שבועות; חלק מהעבודה עשוי לחפוף |
| תאימות לכל קוד מכונה היסטורי | אין אומדן אחראי לפני בחירת תוכנות וממשקים מוגדרים |

אלה אומדני תכנון חדשים המבוססים על היקף הקוד הנוכחי. הם אינם מדידת קצב עבודה, ואינם התחייבות לזמן.

**פערים לפי סדר עדיפות**

כל המאמצים בטבלה הם **אומדנים בלבד**; הם אינם מצטברים בהכרח.

| עדיפות | הפער וחשיבותו | מאמץ גס |
|---|---|---|
| **קריטית** | חפיפת גרפיקה ותוכנית: סכנת השחתת RAM | 1–3 ימים להגנה ממוקדת; ניהול דפים מלא כחלק מהסעיף הבא |
| **גבוהה מאוד** | הכרעת טוקנים ומפרט RAM לפני עוד הרחבות | 2–5 ימי תכנון, ואז שבועות המימוש שתוארו |
| **גבוהה מאוד** | `CLEAR/PCLEAR` ומצביעים: בסיס לתוכניות מקוריות | 3–8 שבועות, בחפיפה אפשרית למעבר |
| **גבוהה** | השלמת תחביר: חזקה, הקסדצימלי, טווח LIST, יעד RUN ופונקציות חסרות | 2–5 שבועות למכלול מוגדר ובדוק |
| **גבוהה** | קלטות מקודדות ו־`CLOADM/CSAVEM/USR` | 2–6 שבועות לאחר קביעת מבנה הזיכרון |
| **גבוהה** | שירותי ⁨`$A000`⁩ והכניסות הישירות | 3–8 שבועות לממשקים המתועדים; לא לכל כתובת פנימית |
| **גבוהה** | בדיקות מול מפרט מקורי: מסך, זיכרון, מספרים וקלטות | 1–3 שבועות לתשתית ולקבוצת מקרים ראשונה |
| **בינונית** | מקלדת, inverse, צליל, `PLAY/DRAW/CIRCLE` | 2–5 שבועות, לפי עומק ההתאמה |
| **בינונית** | ג׳ויסטיק, מדפסת והתנגשות ההרחבה במחסניות | 2–6 שבועות לאחר החלטה ארכיטקטונית |
| **קטנה אך חשובה** | הגנת עבודה לפני טעינת קלטת במעבדה | כחצי יום–יום |

**הצעד הבא המומלץ הוא הכרעה מתועדת במבנה התוכנית והזיכרון, לצד תיקון סכנת החפיפה.** אחריה אפשר להפוך את המצאי הזה לרשימת קבלה: לכל פריט תוכנית מבחן, תוצאה צפויה וראיה. כך ההתקדמות תימדד בהתנהגות תואמת, ולא רק במספר הפקודות שהמחשב מכיר.
